## 26. 07_测试用例

### 26.1 固定结构

1. 范围与基线；
2. 环境及准入；
3. 用例索引；
4. 详细用例；
5. 覆盖与缺口引用；
6. 用例评审记录；
7. 执行记录索引；
8. 验收准出建议。

### 26.2 用例字段

| 字段 | 要求 |
| --- | --- |
| 编号/标题/模块 | 唯一稳定；标题明确验证行为 |
| 需求/页面/组件/状态/API/事件 | 可定位；不伪造 PRD 编号 |
| 优先级 | P0 关键主流程/安全资金阻断；P1 重要交互/异常；P2 辅助 |
| 类型/阶段 | 正常、异常、边界、竞态、权限等；原型、浏览器、接口联调、真机、性能 |
| 前置条件 | 初始状态、账号、权限、配置、服务 |
| 测试数据 | 可复现数据/生成方式；等价类、临界值、空值 |
| 操作步骤 | 编号、可执行 |
| 预期结果 | 与步骤对应；界面/数据/接口/状态/副作用；不写“正常” |
| 预期来源/计划基线 | PRD/批准规则/项目契约出处，计划版本或哈希；实现前固定，变更保留前后依据 |
| 入口/不变断言 | 真实触发位置、当前对象ID、应变化及应保持的数据/父层/上下文 |
| 依赖/待确认 | 规则、阈值、权限、服务未就绪 |
| 执行状态 | 初始未执行；实测后通过/失败/阻塞/不适用 |
| 实际结果 | 未执行留空；不能复制预期 |
| 环境/版本/人/日期 | 未执行留空 |
| 缺陷/证据 | 实测后填写；敏感数据脱敏 |

### 26.3 覆盖要求

必须从业务规则、流程分支、状态、异常生成，不只照 HTML 现状写预期。

覆盖：

- 输入边界、空/非法数据；
- 权限；
- 成功/失败/超时；
- 重复点击/回调；
- 返回/取消；
- 并发更新；
- 恢复；
- 分页/筛选；
- 埋点（仅客户端）；
- 兼容/窄屏；
- 敏感信息处理。

### 26.4 阶段与真实性

- 原型模拟不能替代真实 SDK/支付/鉴权/性能；
- 接口联调、真机、性能用例保留，标依赖；
- 管理后台不写埋点测试，但检查“无后台事件设计/模拟记录”；
- 历史自动化断言须逐条映射与证据支持才可计入；
- 默认全部未执行。

按项目声明的能力组织可复现 fixture：可新增对象、无效目标、空/失败/未知结果及长内容，适用性与重置范围写清，不凭空扩展业务。关联列表、详情及其他端读取同一事实；取消、失败、迟到响应不得产生部分写入或跨记录串写。

预期基线、入口/风险覆盖、工具能力、布局、自修复和最终文件证据统一按本文件第 29.9～29.14 节执行。07记录计划，实际结果从08同源引用，不按HTML现状反推预期。

### 26.5 评审与验收

- 评审状态与执行状态分开；
- P0 全部通过、无阻断问题；
- P1/P2 遗留有影响与计划；
- 实际准出规则由业务/研发/测试评审；
- 07 执行结果按 TC 与批次从 08 同源引用，不另建执行台账。

### 26.6 完成检查

- 全部关键需求/状态/异常有 TC；
- 编号稳定、步骤可复现；
- 无伪造通过；
- 待定预期与正式规则区分；
- 后台用例覆盖筛选/页签/分页/详情/批量/权限/迟到响应/桌面铺开；
- 客户端覆盖触控/返回/输入/列表/授权/异常。

## 27. 08_验证记录与验收映射

### 27.1 固定章节

1. 需求覆盖映射；
2. 验收条件与阶段；
3. 实际验证记录；
4. 失败/缺陷及未验证范围；
5. 复核与执行汇总。

三个主体必须分开：

- **需求覆盖**：证明需求有落点；
- **验收条件**：定义可判定标准；
- **实际验证**：真实操作、结果、证据。

不得把“文档已覆盖”写成“实际验证通过”。

### 27.2 需求覆盖映射

```markdown
| 需求ID及PRD出处 | 业务规则/验收目标 | 本轮范围/优先级 | 页面/组件 | FL/SM/SEQ | 状态/异常 | API/字典/权限 | 事件或不采集原因 | TC | 原型/文档定位 | 覆盖状态 | 缺口/DEC |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
```

覆盖状态：完整/部分/缺失/不适用；每个非完整项写原因。

检查双向关系：

- 需求有产物；
- 页面/组件有需求来源；
- 状态有展示与测试；
- 事件有触发组件；
- TC 有依据；
- 引用可定位。

### 27.3 验收条件

```markdown
| 验收编号 | 来源/业务目标 | 可判定标准 | 验证阶段及方法 | 对应TC/证据 | 责任人 | 确认状态 | 未满足处置 |
| --- | --- | --- | --- | --- | --- | --- | --- |
```

- 验收标准有业务确认才标已确认；
- 责任人未知留空；
- 不超出授权范围；
- 未满足有处置计划。

### 27.4 实际验证表

```markdown
| 检查ID | 检查对象/规则 | 方法与实际操作 | 环境/版本/日期 | 实际结果 | 结论 | 证据位置 | 关联问题/TC | 未验证范围 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
```

结论只用：通过/失败/未验证/不适用（可附“修复后复测通过”，但原始失败保留）。

必须按适用性检查：

- 文件存在、文档头、版本/批次；
- ID 唯一、引用有效；
- 页面/组件/状态覆盖；
- 组件十节完整且与 HTML 同源；
- 客户端事件一致、无后台事件；
- 主流程与异常恢复；
- 端/页面/状态/组件切换；
- 编号标注矩阵；
- 后台筛选/页签/分页/详情/批量/确认/toast；
- 1440/1920 铺开与窄屏；
- 文档阅读器；
- 图示；
- 脚本语法、离线依赖、控制台。

### 27.5 证据边界

必须写明不同方法能证明什么：

| 方法 | 能证明 | 不能证明 |
| --- | --- | --- |
| 文本/结构检查 | 文件存在、字段齐全、计数一致 | 交互与视觉正确 |
| 脚本/VM 渲染 | 渲染不抛错、逻辑分支可达 | 真实浏览器布局、点击、焦点 |
| DOM 断言 | 元素/属性存在 | 用户可见性与遮挡 |
| 截图 | 某视口下视觉结果 | 所有点击可用、其他视口 |
| 模拟接口 | 原型分支表现 | 真实服务/第三方可用 |
| 真实浏览器点击 | 该操作路径的实际结果 | 真机/原生手势/性能 |

### 27.6 用例执行与检查项

- 08 实际验证记录 ≠ 07 用例执行；
- 如执行 TC，必须写 TC 编号、执行批次、被测版本、环境、执行人、日期、实际结果、缺陷与证据；
- TC 状态：未执行/通过/失败/阻塞/不适用；
- 检查结论：通过/失败/未验证/不适用；
- 未执行/阻塞对应“未验证”并写原因；
- 原型阶段通过不自动沿用到联调/真机。

### 27.7 汇总与分母

必须给：

- 检查总数；
- 通过/失败/未验证/不适用数量；“部分完成”只描述覆盖进度，不作为实际检查结论；
- 明确分母与统计口径；
- 失败项是否已处置、是否复测；
- 未验证项及原因；
- 用例总数、执行/未执行数量。

入口覆盖和TC执行分别给分母；补充适用/不适用、阻塞、复测范围及当前版本状态。阻塞计入未验证；历史失败与复测批次保留，不能重复计入当前通过数。

不得隐藏阻塞项，不得把未执行项移出分母。

### 27.8 失败、缺陷与未验证

- DEF 编号、现象、根因、处置、复测；
- 修复前失败记录保留；
- 未验证项写原因、影响、补验方法；
- 不能把“没测”写成“通过”；
- 重复执行保留批次与差异。

### 27.9 完成检查

- 需求覆盖无漏项；
- 验收条件可判定；
- 实际验证有操作与证据；
- 失败/未验证可见；
- 计数与构建产物一致；
- 缺陷关闭有复测。

## 29. 验证与证据规范

本章是验证执行与判定的权威归口；交付范围与附件边界见 `STD-DEL-001`～`STD-DEL-003`，交付闸门见 `STD-GATE-001`。

### 29.1 验证层级

| 层级 | 对象 | 方法 | 能证明 |
| --- | --- | --- | --- |
| L1 结构 | 文件、目录、章节、表格列、ID、引用 | 脚本/文本比对 | 交付结构与一致性 |
| L2 构建 | 02 产物、脚本语法、离线依赖、内嵌数据 | 构建脚本、语法检查、外链扫描 | 产物可打开的基础条件 |
| L3 渲染 | 页面 × 状态、组件解析、图示/文档注入 | VM/无头渲染或真实浏览器加载 | 渲染不抛错、状态可生成 |
| L4 交互 | 主流程、后台联动、弹窗、确认、阅读器 | 真实浏览器点击/输入/滚动 | 该路径在该环境下的实际表现 |
| L5 视觉与适配 | 布局、重叠、横向滚动、窄屏、焦点 | 真实浏览器多视口截图/测量 | 被测视口下的视觉与布局 |

任何一层不能替代另一层。只做 L1/L2 不得宣称“交互通过”；只做截图不得宣称“全部点击可用”。

语法检查单独记录，不能替代动作分发连通或缩放效果；源码中已有的“通过”日志不自动成为本次执行证据。

### 29.2 结构检查（必须）

| 检查 | 判定 |
| --- | --- |
| 10 项主交付物齐全 | 缺一即失败 |
| 每份 MD 有文档头 | 版本、批次、PRD、范围、状态、关联文件、更新时间 |
| 章节齐全 | 各文件固定章节存在且有内容 |
| 页面/组件/状态注册 | 无重复 ID、无孤立引用 |
| 设计配置档案 | `uiProfileId/revision/hash` 已登记，生成物与 00/01/03 一致 |
| 组件注册表与页面组合 | 每个实例引用有效组件/模式/变体/区域且归属当前页面；逐项证明变体被 DOM、有效样式/布局和适用行为实际消费，未登记覆盖、错误归属或仅有声明为失败/未验证 |
| 图示结构 lint | 普通节点有非空标签；边端点、守卫、可达性、终态和 SVG 文本/几何均有效 |
| 组件十节 | 每个组件 1～10 节完整，顺序正确 |
| 事件七列 | 表头固定、列数正确、无后台事件 |
| 用例字段 | 编号/依据/优先级/前置/数据/步骤/预期/状态齐全 |
| 检查项 | CHK 编号唯一、结论合法、证据位置可定位 |
| 计数一致 | 00/01/06/07/08 与构建实测一致 |
| 废弃编号 | 保留且未复用 |

结构检查脚本应输出：

- 文件清单与缺失项；
- 页面数、状态数、组件定义/实例数；
- 组件缺节清单；
- 重复/孤立 ID；
- 事件数（唯一事件名）；
- TC/CHK 计数；
- 图示/文档内嵌数；
- 外链依赖数；
- 脚本语法失败数。

在跨版本交付、修复或回归中，还应输出端/页面/组件/状态/用例的映射清单：旧编号、新编号、映射依据、未映射项和废弃项。不得用页面、状态、组件或用例数量相等替代映射，也不得把修复方的自测计数直接当作独立验收结果。

### 29.3 构建与离线检查（必须）

| 检查 | 通过标准 |
| --- | --- |
| 双击打开 | 本地直接打开，无需服务 |
| 运行资源依赖 | 外部脚本/样式/字体/图片、CSS url、fetch等运行加载依赖为0；不得只扫描src/href |
| 用户主动业务外链 | 允许合法外部导航；标明打开方式和离线/唤起失败反馈，单列数量，不计为运行依赖 |
| 外部脚本/样式 | 0 |
| `@import`/CSS 外链 | 0 |
| 脚本语法 | 全部通过 |
| 页面注册 | 页面数 > 0，端分布正确 |
| 状态渲染 | 全部页面 × 状态无异常 |
| 组件解析 | 十节不完整数 = 0 |
| 图示 | 图源数 = SVG 数；无失败 |
| 图示结构 | 空标签、悬空边、孤立节点、重复节点 ID、空 SVG 文本、零尺寸或关键裁切数 = 0 |
| 文档 | 9 份 MD 全部内嵌，版本可读 |
| 大小 | 可正常打开；无异常膨胀 |

外部链接不得自动请求来完成原型展示，也不得以离线扫描为由删除合法业务入口。`_checks/`仅作证据附件，不得成为HTML运行依赖；链接协议和内容安全仍按第 13.11 节。

### 29.5 检查结论与证据

- 结论只用：通过/失败/未验证/不适用；
- 失败项保留原始结果，修复后另写复测；

- 证据位置写明文件、截图、脚本输出、浏览器版本；
- 统计分母必须公开；
- 不把“检查项很多”当通过理由；
- 不把“脚本存在”当执行结果。

### 29.13 版本证据与封存

每批实际记录包含：规则版本/内容修订/模块哈希、PRD/项目覆盖、预期计划版本或哈希、夹具、被测HTML及相关产物SHA-256、构建/运行ID、真实步骤/对象、实际结果、浏览器/系统/视口/缩放/画布、执行者/时间、日志/截图、缺陷/复测和未验证范围。不存在的证据和历史通过不得继承；未执行实际结果留空。

复跑记录还必须写明执行入口、工作目录或路径解析基准、目标产物相对位置、必要依赖及其版本/获得方式、实际环境值和证据输出位置。运行前确认目标存在且原始字节 SHA-256 与计划一致；脚本复制、移动或重建后不得沿用旧入口假定。自动化工具继续放在交付目录外，交付目录中的证据通过运行 ID 和相对引用追溯。机器可读派生结果使用声明且一致的编码；原始日志原样保留，规范化或抽取结果另存并记录方法。目标、环境、编码或结果无法完整解析时，依赖该材料的通过结论不得封存，应在 08 记录原因和未验证范围；解析异常本身不等同于业务失败。复跑不要求把依赖或框架打包进离线 HTML。

结果保持08唯一台账，07/00引用同源记录；允许08用检查ID/运行ID引用`_checks/`实际记录，执行前不得预填通过。为避免内嵌08与HTML哈希循环，可预置运行ID和证据相对路径，固定主文件后执行，在附件封存最终哈希与结果；HTML运行仍自包含。若将执行摘要写回MD并重新内嵌，则是新产物，旧证据只证明旧哈希，需重新做结构/构建/同源检查和受影响真实回归，不能只替换哈希。构建源与自动化工具仍在交付目录外。

版本证据分别记录：①已批准需求/决策与页面、组件、字段、状态、用例含义的一致性；②最终外部文档、内嵌正文、下载源和注册信息的同源性；③实际入口到结果与恢复的执行证据。三者不能互相代替。比对原始字节时保留哈希；如为排除 BOM/换行使用规范化比较，登记方法与原字节证据。组件十节/计数齐全只证明结构，仍须核对该实例的字段、守卫、结果和适用例外；合法共用模式不因重复文本自动判失败。参考产物的正确行为、共同缺陷、合理替代与未验证分开，不继承另一试跑版本的缺陷或历史通过。

本要求适用于项目自测、交付比较及规则提炼；不新增字数、重复率或组件数门槛，不要求重验无关历史版本。历史生成基线缺失时留空并说明，不以当前HEAD倒填；长评审报告仍按需读取，不进入默认阶段装载。

#### 29.13.1 结果协议与汇总有效性

机器结果在执行前定义字段类型、状态枚举、唯一检查 ID、计划检查集合及汇总口径；状态与错误详情分离，不通过 truthy/falsy 或详情内容猜结果。明细与计划核对后派生汇总：非预期类型、缺字段、重复 ID、缺少/额外检查或汇总不一致均使相应结果协议无效。保留原明细、原计划分母与错误，不能静默过滤后报通过；依赖该证据的通过结论暂不封存，修正协议后重新执行，不能只改通过数量。协议无效不等于被测业务已证实失败。

验证器至少用合法通过、故意业务失败、布尔 false、字符串 `"false"`、字符串 `"ok"`、缺字段、字段错位、重复 ID、漏项和汇总不一致等反例确认能保留失败、拒绝非法输入。若项目选布尔结果，必须严格检查布尔类型；若选状态枚举，则不得混入布尔或字符串别名。非通过状态、执行与适用分母均明确，`detail` 不承载通过状态。

不强制所有项目使用 JSON；受控人工表格亦可，但须有稳定检查 ID、明确状态/依据、计划集合与同源汇总。08 仍是唯一结果台账，附件为其引用记录，不能产生独立结论源。按需示例与反例工具见[自测方法](../docs/acceptance/selftest.md)，工具通过仅证明选定协议检查能力。

`required-check-set` 是上述结果协议的按需门控实现：它可以判定当前必需检查是否具备可封存的协议证据，但不会替项目决定哪些业务检查适用，也不会把门控通过写成08的验收结论。项目若采用它，应在08引用同一运行ID、计划版本和产物哈希；不采用时仍须按本节保存等价的计划分母和结果证据。

### 29.14 准出与报告

按STD-GATE-001判断：适用硬约束无已知违反，各端P0主链和必要验证有当前版本证据，公共入口无未处置的缺失/空动作，无阻断布局。阻断布局指关键动作/关闭不可达、重要信息裁切不可恢复、遮挡导致误操作或违反适用硬约束；普通细节按影响分级，不全部定P0。P1/P2遗留记录影响、计划及接受状态，不擅自当成用户接受。修复方的“已修复”统计、截图或 08 回填不能替代验收方的新批次独立复测；修复后必须重新核对产物哈希、受影响主链和依赖回归。

分别报告计划总数、适用/不适用、已执行、通过/失败/未验证、阻塞及复测范围；TC与入口覆盖分开统计，未执行不可移出分母，平均符合率不能掩盖P0失败或必要验证缺失。能力不足可交评审稿，不能宣称对应验收通过。原型验证不证明真实支付、供应商、鉴权、性能或生产上线。
