## 本次补充改变了哪些判断

按用户说明，本轮采用的来源链为：GPT形成V2.2 → 在V2.2下生成项目初版 → 人工调整/调教形成认可的最终原型 → DeepSeek参考V2.2与最终原型总结V3.0。最终版的价值包括用户补充的布局和交互设计，不能推断成“只给V2.2就自然生成了全部最终效果”。目前没有控制输入、工具和模型版本的对照试验，不能把差异归因于模型品牌。

逐条核对27组规则后，问题应分开处理：

| 类型 | 例子 | 对应处理 |
| --- | --- | --- |
| 既有规则未执行 | 搜索历史、当前端跳转、按记录ID查看、迟到回调隔离、预设不能替代真实流程 | 修实现并增加真实入口回归；避免重复写出多套同义规则 |
| 有效表述弱化或规则冲突 | V2.2明确禁止高保真包装，V3.0该禁令不再明确；V3.0菜单选中态两种写法矛盾 | 修唯一权威条款，摘要仅引用 |
| 项目经验被提炼成过强限制 | 7列硬上限、固定实现命名、可逆操作全部确认 | 按适用性区分行为底线、默认值、实现约定和项目覆盖；变更强制程度先审阅 |
| 有自测要求但不足以约束实际交付 | 写了L1～L5，但最低检查仅抽一条详情/一个高影响动作，且“检查存在”容易被误报成“已执行” | 明确入口覆盖、每端主链、风险分支、证据和准出；修复后回归受影响范围 |
| 人工最终版包含隐含设计 | 详情分区、购买父子层、媒体布局、业务补充 | 抽取可复用模式，本项目固定布局契约；其他项目按PRD选型，不套商城全量功能 |

两版都曾允许少量语义色；用户最新要求“保留交互，使用灰度线框”需要同步覆盖成功、错误、警告和焦点等令牌。不能把原文误述为从来只允许纯灰。中文主显示、隐藏业务多余滑块但保留滚动、本项目以最终版为设计目标已有用户依据。

## 推荐的规范组织

沿用已经确认的模块化结构，不再追加一份需要AI每次全读的超长总提示。

| 层 | 放什么 | 何时读取 |
| --- | --- | --- |
| 通用底线 | 状态/数据/动作/恢复、同源、证据真实性、交付关卡 | 按现有阶段路由加载 |
| 端与能力模式 | 移动/PC/后台；搜索、表格、复合弹层、配置发布等模式 | PRD涉及才加载，已有强制要求不能因“按需”变可选 |
| 经过验证的基础实现 | 外壳、层栈、记录定位、请求隔离、阅读器等可复用代码 | 选定对应实现方案时读取；先具备真实回归证据再升级为推荐基础 |
| 项目配置与布局契约 | 本项目分区/顺序、尺寸覆盖、字段依赖、支付路径、示例数据 | AI根据PRD和适用模式生成；有人工认可参考时精确提取 |
| 验收与证据 | 生成前明确预期，交付前实际执行，失败修复后回归 | 验证阶段按能力读取；结果归07/08，证据作附件 |

“像最终版一样稳定”需要分两种情况：本项目可以把认可版的页面结构、组件层级、关键尺寸和操作路径固定；新项目应稳定遵守同一组布局/行为规则，具体画面随任务变化。用户没有提供参考时，由AI选用默认模式并标出推断；涉及业务阻断的缺口才提交确认，不要求用户先写组件接口和测试脚本。

现有局部参考代码尚没有完整浏览器验收，不能直接宣布已经解决跨模型稳定性。长篇差异报告用于追溯，后续正式执行只读取批准后的相关条款、模式和项目契约。

## AI交付前应怎样自测

建议采用 [具体自测协议](02_通用稳定性与自测协议_待审.md) 中的流程：

1. 实现前从PRD、已批准规则、项目覆盖形成页面/组件行为和布局预期。
2. 声明实际工具能力，形成真实入口清单、风险用例和夹具；用例初始全部未执行。
3. 检查结构、构建、逐页面状态渲染，再执行浏览器点击/输入/滚动及多视口布局检查。
4. 对比应该变化的数据和不应变化的数据，不能只看成功提示、截图或状态预设。
5. AI自行修复已确定的实现错误，同步文档、重新构建，复测失败项及受影响共用能力。
6. 用最终文件哈希绑定执行证据，保留失败和未验证项，再判定能否准出。

无浏览器工具的AI仍可生成评审稿、测试计划并运行能力范围内的检查；不能把这些当L4/L5通过。也不能让用户逐按钮补测成为默认兜底方式。优先由具备相应工具的AI接续同一固定版本验证，缺少能力时清楚保留缺口。
